# Roadmap

Milestones are ordered; each one is measured before the next starts. "Score" means the olmOCR-bench overall score unless stated (see `docs/BENCHMARKS.md`).

| # | Milestone | What it delivers | Done when |
|---|---|---|---|
| M0 | Foundations | Repo, docs, benchmark data on disk, the official scorer running locally | Scorer runs end to end on a trial output folder |
| M1 | Honest baseline | Text-layer-only converter (no models): reading order, paragraphs, headings, simple tables | Full benchmark run; score recorded in BENCHMARKS.md |
| M2 | Structure engine | Layout detection (columns, tables, figures, headers and footers), header and footer removal, heading levels, list detection, hyphenation repair | Beats Marker on multi-column, headers and footers, long-tiny-text, base |
| M3 | Tables | Cell-accurate tables from text layer + ruling lines + a structure model; merged cells as HTML | Beats MinerU 2.5 on the tables section |
| M4 | Formulas | LaTeX for display and inline maths (text-layer aware, model-assisted) | Competitive on the arxiv-math section |
| M5 | Scanned pages | OCR path for pages without a usable text layer (open-source OCR or a small vision model, GPU rental if needed), with the same structure engine on top | Competitive on the old-scans sections |
| M6 | Verification layer | Cross-check every model output against raw evidence; confidence score in front matter; nothing invented | Zero invented sentences on a hand-audited sample |
| M7 | Beat them all | Overall score above every published tool on both public benchmarks | Recorded run, reproducible from this repo |
| M7b | Marks that carry meaning | Ticks, crosses, bullets drawn as shapes, tiny images or symbol-font glyphs read into the text | Icon-based tables in the owner's insurance library convert with their meaning intact |
| M8 | Product polish | CLI, batch mode writing an OKF bundle (`index.md`, `log.md`, `okf_version`), cost controls, docs for new users | A stranger can install and convert a folder of PDFs in 10 minutes |
| M19 | Certainty per document (D039, D040) | On the owner's insurance library: every document checked as it arrives, TrueDoc's own close calls recorded, a second reader, a person asked only what the checks cannot settle, and their answer kept as a lesson that carries to the next issue | A pilot on one or two insurers measures the review load, with confirmations surviving a reissue |

Milestones M2 to M6 loop: build, measure, look at failures, fix, repeat.

## Product shape agreed with the owner (3 September 2026)

Two axes: where TrueDoc runs, and where a model runs.

| | TrueDoc on our website | TrueDoc from the repo, on the user's machine |
| --- | --- | --- |
| Mechanical reading (text layer, layout, CPU OCR) | free tier | free, any laptop |
| Vision stage and "inferred" marks | paid, metered; we call the model endpoint | they point it at their own GPU, a rented endpoint, or our service |

- **M9 - Vision stage (agreed).** One switch, "read unreadable pages with a model", off by default. Behind it one interface ("send this image and this question, get text back") with two providers: an open model (olmOCR 2 today; Chandra worth trying) on a GPU endpoint for transcription, and a frontier model API for understanding. The open model reads pages TrueDoc left empty; the frontier model is for "inferred" work. The endpoint address is the only setting; the rented instance is one such endpoint during development. Licences to check before a paid service: olmOCR 2 (Apache 2.0 [recalled]), Chandra (openrail, conditions).
- **M10 - "Inferred, and say so" (agreed).** A model reads what the mechanical pass could not (icons, charts, unreadable regions, handwriting, unmapped fonts, formulas the rebuild cannot assemble); the result is written with a visible mark and listed in the front matter. The mark: a footnote tag such as `covered under contents[^inferred]` with one definition per document, and a page note for a whole page read by a model. Agreed by the owner on 3 September (evening) and built the same evening for pages, icons in table cells and figures, behind the `--vision-endpoint` switch (served model or `anthropic`), tested against stand-in models. **Done for real on 13 September**: run 91 read 103 pages through Anthropic's API with a key of the owner's, scored 85.4 against the open-weight 84.1, and every page names the model that read it. Off by default; paid tier on the website. See D025 for the two-tier reader and the two scores kept apart.
- **M11 - Library test bed and held-out slice (agreed).** The owner's insurance library is the independent check for every new rule (never scored); a fifth of the benchmark pages is held out and never tuned on, reported separately. Disagreement mining: run the model over pages that have a text layer, diff against TrueDoc, cluster the differences into candidate rules; fit thresholds on model-labelled pages with a held-out set. **The library's own held-out slice is sealed** (D030, 16 September): 19 documents chosen by a hash of their file names, excluded from every measurement and never opened while a rule is being built, to be scored once at a milestone by the insurance set's method and reported separately - `bench/insurance_holdout.txt`. **Step two ran on 16-17 September:** 24 documents from 24 insurers, two pages each, converted and read against their page images. - **M18 - The reader swap, step 2 (census done 8 Sept, ordering discussed with the owner the same afternoon).** Step 1, the census, is done and clean enough: PyMuPDF and PDFium read the same characters on all but about twenty of the 1,403 pages, PDFium is 2.44 times faster, and the two bounded gaps are glyph outline measurement (the maths stage's tall brackets) and raw codes for unmapped glyphs (the 16 Type 3 pages). The alternative to building it at all is Artifex's commercial licence (price on request), which is the owner's call. **Started 9 Sept and stopped at a measured wall (commit 12d9d45; `truedoc/extract/pdfium_reader.py`, `bench/tools/reader_compare.py`). The characters are fine; the lines are the job.** Over 216 benchmark pages with text the two readers agree on reading order at 0.998 median (two pages below 0.9, both with encodings already known to be broken), on horizontal boxes to 0.000 pt median and 0.159 at p90, and on vertical boxes to 0.527 pt - a constant font-ascent convention that does not disturb relative geometry. Two earlier worries dissolved in PDFium's favour: its default character box already *is* the glyph ink extent the formula stage needs (PyMuPDF wants a second, slower pass for that) and its loose box is the metric one, so one pass yields both. **What did not dissolve: PyMuPDF's rawdict hands back characters already grouped into blocks, lines and spans; PDFium hands back a flat run.** Two independent groupers measured against PyMuPDF's lines over 178 pages: a sequential baseline walk (median 0.491 of lines exact, 22 of 178 pages above 0.9) and baseline clustering (median 0.327 - worse). That is not a tuning problem. MuPDF's structured-text device follows the content stream's text operators, font changes and writing direction; reproducing it is days of layout engineering plus several runs, for a change worth at most +0.30 with -0.38 at risk. **Three branches now, not two:** buy the Artifex licence; build the grouper; or adopt a permissively licensed PDFium wrapper that already groups lines - `pdftext` (Marker's, which `docs/M14_MARKER_MINERU.md` records as extracting "spans, lines and fonts, with the character stream position kept per span") or `docling-parse`. **Price the third first**, with one specific question: our formula rebuild needs per-glyph boxes, and M14 also records that Marker never reads formulas from the text layer because pdftext cannot represent maths, so its span model may not carry the detail the 87.4 arXiv score is built on. **Both checked 9 Sept: `pdftext` is Apache-2.0 and `docling-parse` is MIT, so either satisfies D007 with no fee.** And the worry about maths was wrong: pdftext has `PageChars`, `get_chars` and a `keep_chars` option that returns every character's own box, so the per-glyph detail the formula rebuild needs is there - Marker chooses not to use it, which is not the same as it being absent. **The metric that drove the earlier verdict is itself discredited:** three independent implementations reproduce PyMuPDF's lines at 0.49 (hand-written), 0.48 (pdftext) and 0.75 (pdfminer.six), and the 0.48 one is what Marker uses to score 76.0 on this benchmark. PyMuPDF's segmentation is one valid answer among several, not a gold standard, so agreement with it measures nothing. Only a scored run does. **Started for real (commit 1eaf61e): `truedoc/extract/pdftext_rawdict.py` rebuilds PyMuPDF's rawdict shape from pdftext so `extract_page` is unchanged, behind `TRUEDOC_READER=pdftext`, off by default; pdftext installed with `--no-deps` to keep our pypdfium2 5.13.0 against its 5.10.1 pin, which it has been exercised against over 103 pages and 328,000 characters. Baseline established by run 65 (84.0, every check identical to run 64).** First result: the gate scores **71/128 against MuPDF's 100**, and the shape of the loss is the finding - one table page 14 to 0, another 8 to 5, a multi-column page 3 to 0. **The fault is not pdftext: `extract_page` is not the only thing that reads text.** The ruled-table builder calls `get_text("dict", clip=...)` itself, the maths stage re-reads the page with accurate boxes to measure glyph ink, and the extension-glyph origins read again - all still through MuPDF, so they now disagree with the page's own characters about where everything is. Mixing two readers is worse than either alone. **Next: move those three call sites onto the same reader, then re-run the gate.** Two documented approximations in the adapter remain untested because this masks them: a baseline estimated from the metric box (pdftext reports no glyph origin) and no fill colour (which the hidden-text rules of D011 need). The default path is untouched and verified - 286 tests, gate 100/128 with the switch off. **All four call sites moved 9 Sept evening, and the adapter rebuilt on a better division of labour: pdftext decides only grouping and reading order, and every geometric fact is read straight from PDFium by the character index pdftext already carries (`char_idx`).** That removed both approximations - origins and fill colours are now read, not estimated, so D011 works on this path - and uncovered three defects the first adapter had shipped: pdftext rotates its coordinates into display space where PyMuPDF does not, so `extract_page` rotated a second time and every box on a rotated page landed a median 210pt out (15 benchmark pages); the estimated baseline was up to 25.8pt wrong on exactly the maths-extension glyphs it mattered for; and PDFium's font-descriptor flags were passed through into PyMuPDF's span-flag bits, where 0x2 means serif on one side and italic on the other. Measured against PyMuPDF afterwards, character origins agree to a median of 0.000pt on both an unrotated arXiv page and a 90-degree rotated timetable. **The remaining difference is line grouping, and it is now measured rather than assumed.** MuPDF's line breaks match neither a gap rule (best case 5,068 disagreements in 67,591 adjacent character pairs) nor the PDF's own text objects (6,345): it keeps characters together across a 95x gap and splits at small ones, because it follows the content stream's text-showing runs.
